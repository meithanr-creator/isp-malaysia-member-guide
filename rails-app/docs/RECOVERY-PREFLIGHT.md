# Recovery preparation and verification boundary

Production remains **NO-GO**. This tooling prepares the `restore_rollback` case; it does not close it. No current checkpoint, backup, provider restore, restored write, application start/restart, rollback or cleanup was executed when this tooling was prepared. Existing historical receipts and private files are retained.

The existing v1 legacy command bodies remain available for their historical fixed-parent workflow. They cannot be used as a fresh-lease continuation: the Node entrypoints reject a selected fresh lease or an existing fresh prepared release before legacy execution. Fresh preparation never imports credentials through `buildEnvironment`. There are no provider, database, mail, key-rotation or file-deletion operations in the new preparation path.

The rehearsal preflight reads the fixed current lease's `acceptance-fixtures.json` and `prepared-release.json` and its operation's `request.json`. It validates the existing prepared-release schema, exact raw-file hashes, current marker/parent, fixture IDs, application/image/tooling/configuration tuple, deadlines and cumulative reservation. It writes `prepared.json` and `journal.json` with exclusive creation. An existing or partially written preparation is never overwritten or replayed. The fingerprint preflight validates the same inputs without writing them.

The operation directory is fixed to:

`D:/Projects/isp-rails-tools/isp-staging-private/leases/rails-staging-2/recovery/OPERATION_UUID/`

All input directories/files must exist on D, be ordinary files/directories without redirection, and meet bounded size checks. There is no configurable database URL, parent override, arbitrary input/output directory or legacy-path fallback. This change creates no private inputs itself.

## Private request and exact inventory

The request schema is enforced by `prepareRecovery` in `script/recovery-preflight.mjs`; its synthetic fixture in `script/recovery-preflight.test.mjs` is an executable example, not hosted evidence. Required top-level fields are `version:1`, `operation_id`, `lease_id`, `manifest_sha256`, `prepared_release_sha256`, `tooling_source`, `configuration_sha256`, `window`, `checkpoint` and `object_manifest`. Extra fields are refused. Hash the original file bytes, including their actual newlines; do not copy credentials from the fixture manifest into the request.

The window records exact `starts_at`, `action_deadline`, `cleanup_deadline`, `hard_deadline`, `known_spend_usd`, `reserved_usd` and `ceiling_usd:5`. The hard bound is at most55 minutes from start; action admission ends by minute45 with at least ten minutes before the hard end. Cleanup admission has its own deadline. Known cumulative spend plus reservation cannot exceed US$5. Passing arithmetic is not a billing observation or authorization for another window.

Before a populated checkpoint exists, `checkpoint:null` and `object_manifest:null` produce an explicitly incomplete preparation with blockers and every step NOT RUN. A populated checkpoint requires an exact LSN/time, stopped mutations, evidence references for independent reconciliation and inventory, and actual event/publication/Discover uploads plus interest/enquiry data. These declarations are prerequisites supplied by a reviewer, not evidence generated by preflight.

A populated object manifest also requires `checkpoint-inventory.json` in the operation directory. Its raw SHA256 must match `checkpoint.inventory.sha256`. The schema is `version:1`, `operation_id`, `lease_id`, `manifest_sha256`, `checkpoint_lsn` and `keys`. Every key has exact `key`, `state`, `roles`, `ledger_state`, `length` and nonempty `source_refs`. Each source reference has `kind` (blob, managed_upload or revision), `id` and `slot` (draft, preview, published, durable_ledger, pending or tombstone). This inventory must come from independent checkpoint reconciliation of all referenced revisions/attachments and all durable upload-ledger keys. No current database inventory was collected by this preparation.

The object manifest binds that exact operation/lease/fixture hash/checkpoint LSN and the fixed private bucket `isp-staging-private`. Each `objects` entry has exact key, present/absent state, roles, durable-ledger state, byte length, SHA256, complete metadata, backup relative path and a restricted observation reference/hash. The key set and all state/role/ledger/length values must exactly equal the separately sealed inventory: omission, extra keys, duplicates and substitutions fail. Required current and historical draft/preview/published references must all be included, along with durable ledger keys. Preflight cannot discover an omitted key if the independently supplied inventory itself is incomplete; independent reconciliation remains required.

For a present key, preserve `content_type`, `cache_control`, `content_disposition`, `content_encoding`, `content_language` and the entire `user_metadata` map, using explicit nulls for absent headers. Byte hashes must come from the fetched bytes; database scanner metadata is not a replacement for a measured byte hash. Backups use `objects/SHA256.bin` under the private operation directory. The local verifier reads every present backup, computes the actual length/SHA256 and rejects mismatch. Its exclusive receipt is limited to local byte verification; provider metadata/anonymous denial/restored bytes/known-absent keys remain unobserved. It does not modify any key, database row or scan metadata.

Absent observations are allowed only for pending/tombstone durable-ledger scope and carry null byte/hash/metadata/backup fields. A single absent HEAD or DELETE never proves a previous PUT cannot finish. Pending/tombstone records are retained.

`historical_key_references` must contain one logical `recovery-keyset:...#PURPOSE` reference and restricted sealed-archive evidence for each of SECRET_KEY_BASE and the three Active Record encryption key purposes. They identify retained historical material; they do not generate, rotate, expose or hash plaintext secrets. Actual historical-key availability/decryption is an execution prerequisite.

## Exact database and sequence verification

`script/recovery-fingerprint-inventory.rb` is an executable library accepting an existing caller-owned PostgreSQL connection and a current binding/actor-ID list. Requiring it performs no IO or connection. It refuses autocommit, a merely default-read-only session, weak isolation, a writable transaction or a server other than PostgreSQL18. The caller must establish an active repeatable-read or serializable read-only transaction, short statement/lock timeouts, an operation-approved target and the paused checkpoint.

It inventories every public ordinary/partitioned application table and row digest, complete selected table definitions/columns, public schema owner/ACL, constraints, indexes and validity flags, domain/enumeration types, migration identity and decrypted MFA digests. Foreign tables are refused. Fixture actor IDs are derived from the current manifest rather than fixed actor/registry counts.

Every public sequence and every sequence owned by a public table is inventoried, including qualified name, type, owner/ACL, start/min/max/increment/cache/cycle, ownership dependency, associated table/column/default/identity, actual last_value/is_called and populated minimum/maximum/count. Sequence state is not MVCC-isolated; all application/fixture/browser mutation must remain stopped while this inventory and its snapshot/object checkpoint are established.

Comparison requires exact table/schema/MFA/options/ownership/default/high-water fingerprints. It retains both observed sequence states, permits forward gaps using exact integer arithmetic and increment direction, and refuses backward movement, called-state regression, exhaustion/collision or unsupported cyclic ambiguity. PostgreSQL can reserve/cache values and lose unused values after a crash, so exact last_value equality is not a recovery requirement. See [PostgreSQL18 sequence functions](https://www.postgresql.org/docs/18/functions-sequence.html) and [CREATE SEQUENCE/cache behavior](https://www.postgresql.org/docs/18/sql-createsequence.html).

Compatibility is read-only partial evidence. The separate supplied-evidence validator requires every owned sequence, unique generated IDs beyond the relevant populated high-water mark, unchanged options, exact operation/branch/endpoint, ordinary application writes and fresh-connection persisted reads. It executes no writes and returns NOT RUN. Actual write/probe generation is not wired or authorized here.

## Created target, journaling and cleanup

The target guard uses the pinned local official `@neon/sdk 7.5.0` response field names, checked against the [restore API](https://api-docs.neon.tech/reference/restoresnapshot). Snapshot restores create an independent root, described by [Neon's snapshot guide](https://neon.com/blog/three-ways-to-use-your-snapshots). It does not invent a branch snapshot_id, finalize flag or ordinary fork lineage.

The guard binds the actual source snapshot/LSN to a recorded operation-specific POST path/body with finalize_restore:false and no target override, its returned branch ID and completed operation IDs, plus independent project/branch/endpoint readback. Both request and response hashes must occur in the chained journal. The branch must be newly absent from the before inventory, an independent root, nondefault and unprotected. Optional primary is considered only if actually returned; no missing provider field is normalized into an assertion. The endpoint must belong to that exact new branch/project/region, have bounded0.25CU limits and use the exact direct verify-full host. A parent or arbitrary connection URL fails.

These are pure supplied-receipt consistency checks, not a live provider observation or a write-admission token. The returned target explicitly has write_authorized:false. Local journal `source_id` records operation provenance (parent to snapshot to restored branch to endpoint), separately from provider-reported ancestry.

Journal entries are chained, bound to the operation/plan and cannot start the same action twice. Starts require the action or cleanup admission deadline. Ambiguous/error observations and exact discovered resource IDs can still be recorded after expiry; recording evidence never performs a late provider operation. Partial cleanup retains all created IDs and reports unresolved resource/original-endpoint identities. There is no broad orphan purge, bucket deletion, parent sequence reset or automatic mutation retry.

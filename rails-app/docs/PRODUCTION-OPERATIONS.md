## Runtime configuration

Use the host secret manager with the variable names in `.env.example`. Keep production credentials off developer command lines, logs, Git and container build arguments. `APP_HOST` is the exact bare host-provided hostname; optional `APP_ADDITIONAL_HOSTS` is a comma-separated allowlist. Do not use wildcards or URL schemes. Mail and application links use HTTPS. TLS must terminate at a trusted reverse proxy, with direct app ingress blocked. Secure/HttpOnly session cookies and host allowlists are enforced; `/up` and `/ready` are the only host/redirect exceptions and expose no internal details.

`DATABASE_URL` must name PostgreSQL. `DB_SSLMODE` defaults to `require`; prefer `verify-full` with the provider CA/root configuration. Never lower it to plaintext. Use a direct connection for migrations; review prepared statements/advisory locks before adding a transaction pooler. Start with 3 Puma threads and one process, then size database connections against all web processes and operator jobs. A 15-second statement timeout and 5-second connection timeout bound ordinary failures. Set `TEST_DATABASE_URL` only for disposable PostgreSQL CI databases; local development/test otherwise use SQLite.

Generate an independent `SECRET_KEY_BASE` (at least 64 characters) and three independent `ACTIVE_RECORD_ENCRYPTION_*` values (at least 32 characters) outside logs. Keep encrypted MFA secrets/account-delivery tokens and the keys separately backed up. Local/test keys derive from the local secret only and are never production fallbacks. Losing production encryption keys prevents recovery of encrypted data. Rotation requires a reviewed migration/previous-key plan, a staged decrypt/re-encrypt rehearsal and restored backups with the corresponding historical keys; changing an environment value alone is not a rotation procedure. Rotate session secrets with an intentional forced-login plan.

Private uploads use `production_private` S3 service with `public: false`, no-store metadata and HTTPS endpoints. Set AWS region/access key/secret, storage bucket and optional compatible endpoint/path-style setting. Grant only the app's required bucket/prefix list/read/write/delete permissions. Keep R2 public URLs/custom domains disabled and collect evidence that anonymous access is denied. Use supported lifecycle/retention controls and separately protected object backups. Do not assume S3 bucket versioning or AWS block-public-access APIs are supported by R2; verify provider capabilities and restore behavior explicitly. Application configuration cannot certify the bucket's provider policy. There is no public Active Storage/direct-upload route; protected controllers authorize requests and verify the stored bytes against scan evidence.

`ISP_ACCOUNT_EMAILS_ENABLED` defaults to false. Enabling it requires approved `MAIL_FROM`, SMTP address/user/password and mandatory verified STARTTLS (port 587 default). The sender address is a separate approval from the first administrator address. Set `ISP_ACCOUNT_EMAIL_DISPATCHER_ENABLED=true` only when the encrypted outbox dispatcher is scheduled and monitored; the flag does not create a schedule or prove delivery. Public account requests queue encrypted one-use delivery tokens, never send SMTP in the request. Run `bundle exec rails identity:dispatch_account_email` on an operator-managed schedule after approval. Reconcile queued/stale/failed entries, provider rate limits and bounce/complaint feedback; failed or stale dispatch tokens must be revoked and scrubbed. Exercise success, failure, stale lease and duplicate dispatch in staging before release. No email has been sent during preparation.

## Upload quarantine and scanner operation

Every uploaded event image/brochure, Discover image and publication cover/PDF is type/size checked, then scanned synchronously from its request tempfile before Active Storage creates a blob. Tempfiles are quarantine and must stay on a non-public ephemeral filesystem. There is no scanner bypass in production. Infection, malformed/unknown response, timeout, stale signatures, unsupported engine, size limit or scanner outage rejects the upload and preserves the current content. Development keeps local review behavior unless `ISP_SCAN_UPLOADS=true` is explicitly used for a drill.

Run a maintained ClamAV daemon on the same protected private network with `CLAMD_HOST`/`CLAMD_PORT`, UTC timezone, freshclam updates and alerts on updater failure, age and memory pressure. Never expose port 3310 publicly: clamd TCP is unauthenticated. The client uses INSTREAM byte framing, no shell/path interpolation, 64 KiB chunks, a 25 MiB hard limit, 4 KiB response limit, a 3-second connect timeout and 15 seconds per exchange (version then scan). It accepts only the explicitly reviewed supported patch versions in `UploadScanner::SUPPORTED_ENGINES` and signature dates at most 48 hours old (at most one hour clock skew). Keep this allowlist updated as supported ClamAV patches are released. Existing blobs retain their original engine provenance: before removing an old accepted version, inventory/re-scan affected bytes with the new engine or re-upload them under a reviewed migration; otherwise the intended fail-closed check makes those files unavailable. Rehearse that change on staging to avoid an unplanned library outage. [ClamAV network/scanning guidance](https://docs.clamav.net/manual/Usage/Scanning.html), [supported-version policy](https://docs.clamav.net/faq/faq-eol.html).

Configure clamd to reject limit exhaustion rather than report an incompletely inspected file as clean: enable `AlertExceedsMax`, heuristic alerts, PDF/archive scanning and encrypted-document/archive alerts; set `StreamMaxLength` above 25 MiB, file scan limits at least 25 MiB, bounded recursion/files/expanded bytes and scanner runtime under the client deadline. Size memory based on the current signature database and monitor it. Review the installed version's actual configuration names and prove this policy with real clean files, official harmless EICAR test content, malformed/over-limit/encrypted files, outage, timeout and stale signatures. No ClamAV binary/service has been installed or tested here; local scanner tests simulate protocol responses. [ClamAV configuration reference](https://docs.clamav.net/manual/Usage/Configuration.html).

Accepted blobs carry verdict, engine/signature version, SHA-256 of the exact streamed bytes and timestamp. Production publish/serve checks reject historical blobs lacking this evidence, and delivery compares stored bytes with the recorded hash. Start production with a clean database and approved re-uploaded assets. Do not import local SQLite blobs or manufacture clean metadata for them. Shipped allowlisted fallback images are packaged static assets, not uploads; review their content/rights with the release. Malware scanning does not implement safe image re-encoding, PDF sanitization or guarantee harmless content. Image re-encoding/PDF handling policy and real deployment tests remain explicit release decisions.

## Build, migrate and validate

Build the provided Dockerfile in isolated CI: `docker build -t isp-member-rails .`. It runs as an unprivileged user. No runtime credentials are included. `SECRET_KEY_BASE_DUMMY=1` is accepted only for the single `assets:precompile` task; an HTTP server, console, migration or preflight using it fails configuration validation. Asset compilation uses temporary local storage only for that build task. Do not run seeds, `db:prepare`, `db:reset` or sample-data imports in production: sample seeds deliberately raise there.

With the approved pre-created PostgreSQL database and runtime secrets, run exactly one release migration job: `bundle exec rails db:migrate`, then `bundle exec rails production:preflight`. Start web processes with `bundle exec puma -C config/puma.rb`. Migrations are not run automatically on every web boot. Existing jobs/caches are deliberately inline/null until a reviewed durable queue/cache is needed; no missing auxiliary database is silently assumed. Action Cable has no application channels; shared realtime transport must be provisioned before adding such features.

`/up` proves process boot only. `/ready` checks a PostgreSQL connection, pending migrations, authenticated object-service HEAD access, scanner supported version and signature freshness; 503 is a dependency failure. It is unauthenticated, returns no dependency details and does not write an object on every poll. `production:preflight` additionally checks demo accounts/routes are absent and writes, reads and deletes a random private storage probe. It sends no mail. Passing either is not proof of correct bucket policy, malware detection, email delivery, MFA, member eligibility or owner release approval.

CI must run migrations and the independent suite against disposable PostgreSQL as well as local SQLite, then autoload, Brakeman, dependency and asset-build checks. Never point CI at the live database or production bucket. Record the actual hosted image digest, Rails/Ruby/database/scanner versions, checks and operator sign-off. The prepared Windows tests do not claim a Linux image build, hosted PostgreSQL run, private-bucket integration, real malware detection or delivered email.

## Backups, rollback and incident response

Before release, choose database backup frequency, retention, recovery-point/recovery-time targets and an accountable operator. Enable provider automated backups/PITR where available, separately protected object copies and key backups. R2 replication/durability or a private bucket alone does not provide recoverable deleted-object history; prove recovery using the chosen backup arrangement. Restore a database backup and matching objects/keys into isolated staging; verify member access, MFA decrypt/enrollment behavior, event registrations, consultation ownership, publication downloads and upload hashes. Record restore time and data loss. A backup status alone is not a restore exercise.

Before each schema deployment take a named backup and record the prior image digest. Use backward-compatible schema changes. Roll back the web image only while its schema contract still holds; otherwise restore/replay data under an approved incident plan. Do not automatically run destructive down-migrations against live member/payment data. Rehearse this on staging before switching traffic.

Monitor HTTPS availability, 5xx/readiness failures, latency, DB connections/storage/backup status, private object errors, scanner freshness/update/memory, authentication throttles, outbox delays/failures and administrative actions. Alerts require a named recipient and response procedure; no automation/notification has been created. Log request IDs and generic error categories, exclude tokens/passwords/OTP, imported references, enquiry bodies, contact details and bank/receipt data, and restrict access/retention. Avoid debug logging in production.

For suspected account compromise revoke sessions/tokens, suspend affected accounts, preserve restricted audit evidence and rotate relevant secrets after assessing scope. For a scanner/storage failure stop uploads and keep the failure gate in place; never bypass it to restore availability. For data loss stop writes, preserve current evidence, restore into isolation and verify before reopening. The owner must approve privacy/retention/deletion rules, finance reconciliation/support roles, identity recovery and incident ownership before activation. Shop and Jobs remain frozen.
